# Agnet 深度学习
## what is Agent
Agent目前主要有2种解答方式，一种是能够长时间独立运行，利用各种工具完成复杂任务的全自主系统，另一种描述是遵守定义好的工作流执行执行指定的内容。我的观念偏向Anthropic对Agent的定义。
- Workflow：工作流就是程序提前规定好的流程，LLM和工具只是按照这些步骤执行。读取文章
```java
→ 提取正文
→ 调用 LLM 总结
→ 按格式输出
```
- Agent：让系统LLM根据任务进行，自行决定处理流程和工具的使用
```java
搜索资料
→ 打开几个网页
→ 提取价格和配置
→ 发现信息不完整
→ 再搜索其他来源
→ 对比结果
→ 整理成报告
```
## 什么时候去使用Agent？
不要为了流行而用Agent，就像以前Java生态的时候为了流行Spring cloud而用Spring Cloud。先用最简单最可控的方案，当真的需要自主决策的时候在使用agent。
可能的方案层级是：
```java
一次 LLM 调用
→ 加检索和示例
→ 固定工作流
→ Agent
→ 多 Agent 系统
```
不要一开始就上多 Agent、长期记忆、复杂编排。

有些问题不需要 Agent。普通代码、一次 LLM 调用，或者一个固定工作流，可能已经足够。
例如：
- 把一段文本翻译成中文；
- 从发票中提取金额和日期；
- 按固定格式生成摘要；
- 判断用户问题属于哪一个分类。

**Agent的流程是**

思考
```java
→ 调工具
→ 查看结果
→ 再思考
→ 重试
→ 调另一个工具
```
因此会出现响应变慢，Token和Api费用变高，出错的可能更多，调试和评测困难 。

## 增强LLM
其实Agent就是一个能够访问外部信息，调用工具并管理状态的LLM。
其实也就是增强LLm Augmented LLM
```
Augmented LLM
= LLM
+ Retrieval（检索）
+ Tools（工具）
+ Memory（记忆）
```
### 检索 Retrieval 
模型可以获得出训练数据以外还可以去搜索互联网 查询公司知识库，查找项目文档，查询数据库。

例如用户问：
对比最近三款手机的续航能力。

模型可能自己生成：
```
“手机 A 电池续航评测”
“手机 B 视频播放续航”
“手机 C 实际使用续航测试”
```
### Tools：工具
让模型不仅能够“说”，还能够执行操作，例如：
- 使用计算器；
- 执行代码；
- 查询天气；
- 创建日程；
- 读取文件；
- 调用业务 API。
模型会根据当前任务选择适当工具：
需要最新资料 → 搜索工具
需要精确计算 → 计算器
需要分析 CSV → Python 工具
需要订单状态 → 订单查询 API
```json
{
  "tool": "search_orders",
  "arguments": {
    "order_id": "A123"
  }
}
```
### Memory：记忆
让系统保留以后可能需要的信息，例如：
- 当前任务的进度；
- 用户偏好；
- 之前的工具结果；
- 已经尝试但失败的方法；
- 跨会话的重要信息。
不过 LLM 本身并不天然拥有永久记忆。通常是应用提供数据库或记忆工具，模型决定：
哪些信息值得保存
→ 调用 memory_write

需要哪些历史信息
→ 调用 memory_search

**总结一句话来说，带索引、工具和记忆的模型**实现它的关键不是介入尽可能更多的模型，而是提供与业务匹配、描述清晰、权限受限的能力 。

## 工作流 提示词
不要让LLM完成整个复杂 的 任务，而是把任务拆分成 多个固定小步骤，前一步的输出，作为后一步的输入。
```json
用户需求
   ↓
LLM 1：生成文章提纲
   ↓
Gate：检查提纲是否合格
   ↓
LLM 2：根据提纲写初稿
   ↓
LLM 3：润色初稿
   ↓
最终文章
```
因为如果一个LLM顾及多个地方，可能会出现很多的地方顾及不到。
```json
用户需求
   ↓
LLM 1：生成文章提纲
   ↓
Gate：检查提纲是否合格
   ↓
LLM 2：根据提纲写初稿
   ↓
LLM 3：润色初稿
   ↓
最终文章
```

## 工作流 routing 路由
先判断输入属于哪一类，再把它交给最适合处理该类别的流程、提示词、工具或模型。
```json
用户问题
   ↓
Router：判断问题类型
   ├── 普通知识 → FAQ 工作流
   ├── 退款申请 → 退款工作流
   ├── 技术故障 → 技术支持工作流
   └── 无法判断 → 人工客服
```
Routing 不只能选择业务流程，还可以选择不同能力和成本的模型
```java
用户问题
   ↓
评估难度
   ├── 简单、常见 → 小模型
   ├── 中等难度 → 中型模型
   └── 复杂、罕见 → 强模型
```
### 什么时候使用 routing
适合：
- 输入存在几个边界相对清楚的类别；
- 不同类别需要不同提示词或工具；
- 分类准确率足够高；
- 各个分支可以独立优化；
- 希望控制成本和权限。

不太适合：
- 类别高度重叠，难以准确区分；
- 一个请求经常同时包含多个类别；
- 每次任务所需步骤完全不可预测；
- 分错类别会造成严重后果，却没有复核机制。

### Routing 和 Agent 的区别
Routing 通常仍然是固定 Workflow：
而Agent是自我决定需要那些能力，是否拆分任务，下一步进入那个流程，是否返回上一步重试。
## Workflow Parallelization  并行化
让多个 LLM 调用同时处理任务，最后再由程序汇总结果，而不是让它们一个接一个执行。
```json
                   ┌→ LLM 调用 A ─┐
用户输入 → 拆分/复制 ├→ LLM 调用 B ─┼→ 程序汇总 → 最终结果
                   └→ LLM 调用 C ─┘
```
它主要有两种模式：
1. Sectioning：不同调用负责不同子任务；
2. Voting：多个调用完成同一个任务，再综合判断。
### Sectioning：任务分区
```json
合同
 ├→ LLM A：检查法律风险
 ├→ LLM B：检查商业风险
 ├→ LLM C：检查数据隐私条款
 └→ LLM D：检查语言歧义
             ↓
          合并结果
```
```c++
//伪代码
results = await gather(
    check_legal_risks(contract),
    check_business_risks(contract),
    check_privacy(contract),
    check_ambiguity(contract),
)

final_report = merge(results)
```

Guardrail 示例
文章中的第一个例子是将正常任务和安全检查并行执行：
```json
用户请求
 ├→ LLM A：生成正常回答
 └→ LLM B：检查请求或回答是否违规
             ↓
        程序决定是否展示回答
```

与让同一个模型同时“回答问题”和“检查安全”相比，职责分开通常更可靠：
- 回答模型专注于内容质量；
- 安全模型专注于风险识别；
- 最终由程序决定放行、拒绝或交给人工。

什么时候适合并行化？
适合以下情况：
- 子任务之间相互独立；
- 可以在一开始就确定所有子任务；
- 希望缩短执行时间；
- 一个问题包含多个需要分别关注的维度；
- 需要多个独立意见提高可信度；
- 漏检的代价较高。
不适合：
- 后一步必须使用前一步的结果；
- 子任务之间存在复杂依赖；
- 任务非常简单，一次调用已经足够；
- 成本比延迟更加重要；
- 最终结果很难可靠地合并。


### Voting：多次尝试或投票
Voting 不是把任务拆开，而是让多个 LLM 调用处理同一个任务：
```json
同一份输入
 ├→ LLM A：做一次判断
 ├→ LLM B：独立做一次判断
 ├→ LLM C：换一种提示方式判断
 └→ LLM D：从另一个角度判断
             ↓
        投票或综合结果
```
它类似于请几位评审独立发表意见，而不是把工作分给不同部门。
例如进行代码安全审查：
```
同一段代码
 ├→ 审查 A：寻找 SQL 注入
 ├→ 审查 B：以攻击者视角分析
 ├→ 审查 C：寻找权限绕过
 └→ 审查 D：自由安全审计
                 ↓
           汇总全部风险
```
这里既包含相同任务的多次尝试，也可以通过不同提示词产生不同视角。

并行化就是让多个 LLM 同时分工或独立判断，用更多计算成本换取更低延迟、更全面的关注或更高的判断信心。


## WorkFlow Orchestrator–Workers（协调者—执行者）
Orchestrator–Workers 是由一个中央 LLM 根据当前任务临时制定分工，多个 Worker 分别执行，再由中央 LLM 验证和综合结果；它与普通并行化的关键区别是，子任务不是提前写死的。
```json
复杂任务
   ↓
Orchestrator：理解任务、动态拆分
   ├→ Worker A：执行子任务 A
   ├→ Worker B：执行子任务 B
   └→ Worker C：执行子任务 C
                  ↓
Orchestrator：检查并综合结果
                  ↓
               最终答案
```
什么时候适合使用？
适合：
- 任务复杂，难以提前确定子任务；
- 不同输入需要完全不同的分解方式；
- 子任务可以相对独立地执行；
- 任务涉及大量文件或资料来源；
- 单个模型上下文容易过载；
- 最后可以通过测试或证据验证结果。

典型场景包括：
- 跨多个文件修改代码；
- 深度资料研究；
- 大型文档分析；
- 复杂审计；
- 根据数据动态生成分析计划。

不太适合：
- 步骤固定而且容易预先定义；
- 任务很简单；
- 各个步骤高度依赖，无法独立执行；
- 拆分和汇总的成本超过任务本身；
- 缺少可靠方式检查 Worker 的结果。
## Workflow Evaluator–Optimizer（评价者—优化者）工作流。
Evaluator–Optimizer 是“生成者写、评价者审、生成者根据意见再改”的循环，适合质量标准清晰、反馈可执行，而且多轮修改确实能提高结果的任务。
```json
任务
 ↓
Generator：生成初稿
 ↓
Evaluator：按照标准评价
 ├── 合格 → 输出最终结果
 └── 不合格 → 给出具体反馈
                    ↓
           Generator：根据反馈修改
                    ↓
             Evaluator：再次检查
                    ↓
                  ……
```

## Agent
开发者规定目标、工具、权限和边界，由 LLM 根据执行过程中获得的环境反馈，动态决定下一步行动。
Agent一个经典 的循环是
```java
用户提出目标
   ↓
Agent 澄清需求
   ↓
制定或更新计划
   ↓
选择并调用工具
   ↓
获得真实环境反馈
   ↓
判断任务进展
   ├── 信息不足 → 继续调查
   ├── 执行失败 → 分析错误并换方法
   ├── 需要判断 → 询问用户
   ├── 达到目标 → 返回结果
   └── 超出限制 → 停止
```
它与固定 Workflow 的区别是，开发者没有提前写死：
```
workflow：先执行 A，再执行 B，最后执行 C
```
Agent 可能根据结果临时决定：
```
agent:
先查看文件
→ 发现问题不在那里
→ 搜索另一个模块
→ 修改代码
→ 测试失败
→ 阅读错误信息
→ 修改测试或实现
→ 再次运行测试
```
## 为什么现在 Agent 越来越可用？
文章提到 LLM 的几项关键能力正在成熟。
1. 理解复杂输入
Agent 可能需要理解：
- 较长的任务说明；
- 整个代码库的结构；
- 多份文档；
- 网页或屏幕状态；
- 用户提出的多个约束。
如果连目标都理解不准确，后续自主行动只会放大错误。
2. 推理和规划
模型需要判断：
- 当前目标是什么；
- 还缺哪些信息；
- 下一步采取什么行动；
- 哪些步骤有依赖关系；
- 是否需要修改原计划。
计划不一定只在开始生成一次。成熟的 Agent 应根据环境反馈持续调整。
3. 可靠地使用工具
Agent 不仅生成文字，还需要正确地：
- 选择工具；
- 填写参数；
- 理解工具返回值；
- 处理失败；
- 避免不必要或危险的调用。
4. 从错误中恢复
例如代码 Agent 修改后测试失败：
运行测试
→ 得到错误堆栈
→ 分析失败原因
→ 修改实现
→ 重新测试
错误不一定代表任务终止；它也可以成为下一轮决策的输入。


agnet开始任务的时候如果用户描述的不清楚它会询问用户比如
优化速度还是设计？
哪些页面在范围内？
是否允许修改后端？
有什么验收标准？

如果遇见了高风险工作会返回给人类确认
```json
人类规定目标和边界
          ↓
Agent 在边界内自主行动
          ↓
高风险决策或阻塞点返回人类
```


### Ground truth：环境中的真实反馈
Agent 不能只依靠自己的语言推测任务是否完成，必须不断从真实环境获得可验证的反馈。
- 编译器；
- 单元测试；
- 类型检查；
- Linter；
- 实际程序；
- 相关命令。


Agent 听起来很复杂，但最基本的实现本质上只是一个循环：
LLM 决定行动
→ 程序执行工具
→ 工具结果返回 LLM
→ LLM 再决定行动


Agent 本质上是一个带工具、状态和限制的 LLM 循环：模型行动，环境返回真实结果，模型据此调整下一步；它适合路径无法提前写死的开放任务，但必须配合可验证反馈、权限边界、停止条件、沙箱和必要的人工确认。
